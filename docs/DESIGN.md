# AnyKey 设计思路（DESIGN）

> 本文解释 AnyKey 各项核心功能**为什么这样设计**。你不需要读代码，只需要知道：AnyKey 是一个 Windows 键鼠重映射工具，它能拦截你的键盘鼠标输入、按你定义的规则改写后再交给系统。模块划分见 [`CODEMAP.md`](../CODEMAP.md)。

## 0. 总纲：两点根本不同，三类固有难题

### AnyKey 与其他重映射工具的两点根本不同

**其一：Defer 延迟决策——让任何键都能当「按住切层」键。**

「按住某键临时换一套键位」本是最自然的扩容手段，但在大多数实现里它只能绑在 Ctrl/Shift 这些低频修饰键上。普通字母键一绑上去，就立刻撞上"你到底想单击还是想按住"的困境：不等吧切错层，等吧打字全是延迟。AnyKey 不回避这个矛盾，而是专门造了一套系统正面解决它：

- 判定结果没出来之前，这期间敲下的后续按键**既不丢弃也不错发**，而是被暂存起来，待尘埃落定后按正确语境补发；
- 每个键的 hold 判定阈值**各自独立**，哪个手指反应慢就单独给哪个键放宽，手感是逐键调出来的，而不是全局一个参数迁就所有手指。

这让「按住翻页」从一项受限于修饰键的特殊技巧，变成可以随意赋予任何按键的通用属性。（这套机制如何运作，见 §7。）

**其二：天生面向多设备的统一映射管理。**

许多同类工具眼里只有一块键盘：鼠标要么完全管不了、要么只能代发几个固定按键；多键盘更是超出管辖范围。AnyKey 在设计之初就把「哪台设备、当前在哪个应用」当成映射规则的第一维度，把「哪些设备共享同一套运行状态」当成另一个独立维度——多键盘与鼠标不是后期打补丁的兼容层，而是架构的原点。外接一块小键盘当宏板、在键盘上切层让鼠标跟着走，都是原生能力。（映射与状态如何拆分，见 §8。）

### 即便如此，仍绕不开三类固有难题

做输入重映射，还有三个根本困难贯穿始终：

1. **意图不确定** —— 一个键被按下时，「单击」和「按住」在按下瞬间是完全一样的电信号，软件无法读心。TapDance、层切换、Defer 全部是在解决"猜意图"这个问题。
2. **环境会变** —— 同一个键在游戏里和在剪辑软件里应该有不同含义；你有两台键盘一台鼠标，状态怎么算？应用感知与 Runtime 拆分解决这个。
3. **工具自身会坏** —— 一个接管了键盘的程序一旦卡死，用户的键盘就整个失灵。安全网三层防护解决这个。

带着上面两点不同和这三条难题，看下面的每一节。

## 1. 整体架构：为什么要拆成四个独立程序

**问题**：如果把「配置编辑界面」和「后台运行逻辑」写在一个程序里——编辑窗口开着才管事（窗口关了键盘失控），界面崩溃殃及按键处理，开机自启还得拉起一整个大界面。

**方案**：拆成四个各司其职的部件：

| 部件 | 角色类比 | 生命周期 |
|------|---------|---------|
| GUI 配置器 | 图纸设计师：画好配置存盘 | 打开才有，关了就退 |
| 系统托盘 | 值班管家：启动/暂停/重载引擎 | 常驻后台 |
| Rust 引擎 | 大脑：逐个事件判定输出 | 托盘管理，随启随停 |
| 内核驱动 | 装在大门口的闸机：真正拦下每个硬件信号 | 随系统加载 |

**关键约定**：四个部件之间唯一的共享真相是硬盘上的同一个 `anykey_config.json`。托盘要重载就直接读盘，不等 GUI；写入用原子替换 + 防抖，避免读到半截文件。

**生命周期取舍**：
- GUI 关闭 → 引擎照常跑（图纸已归档，施工不需要设计师在场）；
- 托盘退出 → **级联**关停引擎和 GUI，保证不留一个看不见、还在劫持键盘的残留进程；
- 启动时如果配置或引擎缺失，托盘静默待机而不是弹错退出——它毕竟是常驻程序，崩溃式报错只会让用户莫名其妙。

**历史决策：为什么只剩一个 Rust 后端**。早期为了快速验证想法，AnyKey 同时接过三个后端：把配置直译成 AutoHotkey 脚本、AHI 驱动方案、移植 Kanata 配置。三后端并行很快暴露出问题：每个新功能要写三遍；三套实现的行为细节永远对不齐（同一个 TapDance 在三个引擎里是三种手感）；测试要在三条链路上各验一次。2026 年 7 月起全面收敛为唯一的 Rust 引擎——功能语义以它为唯一真相，旧后端连同兼容层一并删除。代价是放弃成熟引擎的现成能力，换来的是一套可测试、可审计、行为可预测的代码。

## 2. 引擎的心脏：一条流水线

引擎内部不是一堆 if-else，而是一条**固定顺序的处理流水线**：每个按键事件像包裹一样依次经过各个站点——组合键判定 → 延迟决策 → TapDance 判定 → 层切换解析 → 最终提交发送。松开事件走一条对应的回流线。

两个要点：

- **加新功能 = 加新站点**，不用推倒重来。后来加入的 Leader 序列就是只挂了钩、没动过原有站点的顺序。
- **单一出口**：不管哪个站点决定了最终输出，都汇到同一个「发送口」统一发出去。如果有多个地方各自直接往系统发键，就可能出现"A 功能发了一半 B 功能又补一刀"的幽灵键。

## 3. Combo 组合键：「同时按下」其实不存在

**问题**：人的两根手指永远做不到真正同时按下 j 和 k，中间总有几毫秒到几十毫秒差。那什么算「组合」、什么算「先按 j 再按 k」？

**方案**：时间窗。两键先后落下的间隔小于 `comboTime`（默认 200ms）就算一次组合。例：`j + k → Esc`。超过窗口就如实输出 j 和 k 本身。

**取舍**：
- 窗口太短容易漏判，太长会把正常打字连击误判成组合——所以做成可调参数。
- 组合一旦成立，输出后流程**直接结束**，不再参与层切换或 TapDance 的后续判定。组合键就是组合键，语义简单不纠缠。

## 4. TapDance 点按：给一个键四种身份

**问题**：物理键不够用时，让同一个键靠「按法」区分身份：

- 单击 = A 功能
- 按住 = B 功能
- 快速双击 = C 功能
- 双击后按住 = D 功能

典型例子：`Ctrl` 单击还是 Ctrl，快按两下变成 `Home`（跳行首）。

**设计决策**：身份表是**每键 × 每层**独立的——同一个键在基础层和功能层扮演不同角色是天经地义的事，所以不做全局回退。三种判定阈值（长按多久算 hold、双击间隔多窄算 dbl tap、双击后按住多久算 dbl hold）各自独立可调，留空即关闭该触发方式。

## 5. 层与三种激活方式

**问题**：把上百种改键塞一层没人背得动。层的思路类似手机键盘：平时一套布局，需要时切到另一套。

**模型**：基础层 `base` + 若干功能层 `fn1/fn2/...`。把某个键的行为设成 `{fn1}` 之类，它就成了层激活键。难在「怎么激活、什么时候回来」，所以有三种语义不同的激活键：

| 写法 | 行为 | 类比 | 适合 |
|------|------|------|------|
| `{fnX}` | 按住期间临时换层，松手回原层；激活键自身的自动重复照常透出 | 按住 Shift 打大写 | 按住当方向键滚动（要连发） |
| `{bnX}` | 同样按住临时换层，但把激活键自己的重复**吞掉** | —— | 按住只做修饰，自己别出声 |
| `{tnX}` | Toggle：按一下固定停在 fnX，抬手也不翻回；`{tn0}` 清空全部回到 base | CapsLock / 数字小键盘开关 | 一键进入游戏层常驻 |

`{fnX}` 与 `{bnX}` 在引擎内部其实是同一件事，差别只影响**激活键自己**按住期间要不要把重复透出去——别的键的解析完全一致。

**`{tnX}` 最难的坑：回到哪一层？**

你可以在 base 层按 `{tn1}` 进剪辑层，然后在剪辑层里再按绑定好的 `{tn2}` 进入更深的层……关掉 tn2 之后应该回哪？早期实现用「计数器」：每激活一次记个数、每次键抬起递减。但固定层**抬起时不该还原**，计数器就永久错位了。重构后的解法是把状态收敛为**唯一的层栈**：进新层压栈；离开时按「是谁离开的 + 要离开哪一层」精确弹出对应条目。数据源只有一个，天然不会对不上账。

## 6. Leader 序列：把操作压缩成前缀码

**例子**：设定序列 `h i → hello` 之后，快速依次按下 h、i 就自动输出 hello。这是 Vim 式的「先按前缀，再跟代码」思路，用来弥补单键数量不足。

几个不容易想到的设计约束：

- **只在键真正会被发出时记录**。判定位置选在「逻辑键已定稿、尚未发送」的时刻——被层吞掉的键、被宏替代的键永远不会混进序列，避免记录到假输入。
- **贪婪匹配 + 死路清栈**。多按一会看看能不能匹配更长的序列；一旦发现当前按键让所有候选都走死了，立刻清掉缓冲放行，不让用户感觉卡顿。
- **循环捕获可选**。输出的内容可以再流回流水线继续匹配，支持"A 序列的输出正好是下一序列开头"的自驱动串联。
- **防无限递归**。序列至少两个键，且宏和层键禁止作为序列成员——否则一个序列的输出若又能触发序列，就会自我循环烧死 CPU。

**屏蔽模式**：有些场景你不希望序列的中间按键漏进系统——比如用 `em → 邮箱地址` 自动填表时，不想要 `emJohn@...` 这样前后混着来。把某个键的行为设为虚拟键 `{leader}`，它就成了屏蔽开关：按下后它和**后续所有按键都被吞掉**、不发给系统，直到序列命中（只输出结果）、匹配失败或超时。代价是这段盲打期里你看不到自己敲了什么，所以它是个可选开关而非默认行为。

## 7. Defer 延迟决策：全项目最抽象也最关键的机制

用一个场景讲清楚。

**场景**：你把 A 键设为「按住 = 进入 Fn 层，轻击 = 输出 A」。现在你按着 A 想敲 Fn 层里的键。

**难题**：A 被按下的那一刻，引擎面对的是一摸一样的电信号——它不知道你是想「按住当层键」还是「马上松手当单击」。必须等一等才能确定。可就在这段犹豫期里，你的手指已经把下一个键敲下去了。这个键怎么办？

- 直接放行？万一是 Fn 层专属的键，放错了。
- 拦下来？万一你只是轻击了一下 A 接着正常打字，这批字就被无端卡住了。

**方案**：把这些拿不准的后续键**挂起（defer）**，等 A 的身份尘埃落定之后——超时判 hold、或者提前判定 force-hold、或者抬起判 tap——再按正确语境**补发**它们。就像快递员收到地址没填完的包裹，等收件人补完门牌号再投递，而不是猜一个地址送错。

配套的两条规矩防止机制失控：

- 不是见键就挂：如果后续键自己也绑定了层行为、或在目标层有自己的 TapDance 定义，说明它也想参与这场"猜意图"，那就让它一起等判定而不单独挂起。
- 同一时间最多只有一批悬而未决的键。两个"犹豫中的层键"叠在一起会让分支数量爆炸，所以这是硬性不变量。

## 8. 应用感知与设备隔离：映射、状态分开管

**用户痛点举例**：
- 打游戏时不想让重映射抢 WASD；
- 剪辑软件里想要一套专用快捷键；
- 两台键盘一台鼠标同时用：在键盘上进了「剪辑层」之后动鼠标，鼠标也应该处于剪辑层语义下。

**两句白话拆解 Runtime 设计**：

- **映射**（这个键是什么意思）跟着「**哪台设备 + 当前前台应用**」走。同一台设备在不同应用下可以用不同规则表；没有专门配置的应用，回落全局默认，不必为每个应用复制一份完整配置。
- **运行状态**（当前在第几层、哪些键还按着、combo 缓冲到哪了）跟着「域」走。**同一个域内的键盘和鼠标共享状态**——这正是上面第三个痛点想要的："键盘切的层，鼠标也知道"。

**计时器为什么要带快照**：宏里可以有 `{Sleep 500}` 这样的延迟。500ms 后前台应用可能已经换了，如果定时器到时候再去问「现在的环境是什么」，就会用错规则。所以定时器创建的那一刻就把当时的映射抄一份带走，醒来按快照干活。

**怎么知道前台是什么应用**：主路径是听 Windows 广播的「前台窗口切换通知」；但这种通知偶尔会丢（系统繁忙或个别怪异窗口）。所以另有一个每 500ms 主动核对一遍的兜底巡查。两者都遵守同一条纪律——回调里只举旗子说"好像变了"，真正的进程名查询放到引擎的空闲处去做，保证按键盘的热路径零额外开销。

**为什么识别放在管道外面**：让管道内部永远只看到"一份现成的环境"，它就不需要理解设备 GUID、进程名这些杂事。边界上一次性解决，核心保持简单。

（本节的白话设计对应的数据结构与实现细节，见 [`CODEMAP.md`](../CODEMAP.md) §9。）

## 9. 内核过滤驱动：为什么要碰内核这种麻烦的东西

**备选方案都不够格**：

- `SendInput` 只能往外发事件，拦不住硬件原始输入，谈不上重映射；
- 用户态钩子/ interception 类方案站在内核之外，任何时刻都可能被杀掉或失效；
- **UpperFilter 内核驱动**插在键盘/鼠标驱动栈的必经之路上，能真正截获并改写每一个硬件级事件——而且绕开了 Interception 方案臭名昭著的设备上限：它的架构决定**全系统最多只能挂 10 个输入设备**，AnyKey 的驱动不走那条路，接多少台键鼠都不受限。

代价是必须签内核驱动（本项目目前只能跑在 Test Signing 模式，见 README 专门章节）。

**默认透传，而不是默认接管**：驱动只对白名单（订阅）内的设备进入拦截态，名单外的设备完全直通——新插一个没配置过的设备，它就是一块普通键盘，零风险零开销；你明确勾选订阅之后，它才被接管。

**设备识别为什么有「透传捕获态」**：拦截态下按键都被吞掉改写，你没法靠「随便按几个键」认出哪块板子是哪块。所以驱动有第二个形态：识别期间不吞键，事件照常发给系统（打字完全正常），同时镜像一份入队给用户态比对——在 GUI 里按下目标键盘的任意键，对应设备行就地亮起。实现上有个隐蔽的坑：识别请求和配置刷新共用同一个设备句柄，并发会把自己锁死，所以识别期间配置刷新是明确禁用的。

**键盘 + 鼠标共用一份驱动的取舍**：两套驱动意味着双倍的安装、签名、维护成本。合一后用一个控制设备、全局状态、心跳看门狗全都是一份。但两个保护措施必须做：

- **移动事件永远直通系统**——光标延迟是肉眼可见的灾难；是否旁路入队由运行时开关控制，只有确需监听时才打开。
- **键盘、鼠标各自独立队列**，只有唤醒等待合用一个——否则高速甩鼠标产生的海量移动事件会把键盘事件挤压饿死。

**设备类型判定用类 GUID 而不是字符串匹配**：同一个物理设备往往既报键盘接口又报鼠标接口，靠名字猜很容易翻车，GUID 是系统给的权威答案。

## 10. 失控安全网：预设一定会崩，只是不知道何时

**前提共识**：这是一个接管了键盘的工具。它卡死 = 用户键盘整个失灵 = 比 99% 的普通 bug 都严重的事故。所以可靠性优先于新功能，且必须预防三种互不相同的故障方式。

三个守护者**故意互不共享检测信号**——任何一个自己坏了，不会连坐另外两个：

| 守护者 | 防的是 | 怎么工作 |
|--------|--------|---------|
| 会话哨兵 | 引擎进程消失（含被任务管理器强杀） | 内核侧持有引擎打开的句柄；句柄消失 = 人没了，立即恢复直通 |
| 心跳看门狗 | 引擎僵死但不退出的假活 | 引擎活着就每 5 秒报一次平安；30 秒收不到才动手 |
| 紧急脱离 | 主线程死锁但心跳线程侥幸还活着的最后盲区 | 你手动按 `LCtrl + Space + Esc` 三键 |

两条容易被忽略的设计细节：

- **心跳取代了老的按键轮询看门狗**。旧方案逻辑是"多久没输入就当出事了"，结果用户安静看一小时视频就被误杀一次。心跳只在引擎真报不上来时触发；计时用单调时钟，不怕系统时间被人手动拨来拨去。
- **紧急脱离为什么必须放内核里检测**：等到需要它的时刻，引擎的用户态代码已经彻底动不了了——靠出事的程序自救是不可能的，只能由还没受牵连的内核代码出手。检测点放在驱动最贴近硬件的事件回调里，每个键都要路过那里，因此三键同时按住总能被看见。触发后的动作不止"放开拦截"：还会清空滞留队列、把所有仍处于按下状态的修饰键（Ctrl/Shift/Alt/Win）模拟一次抬起——否则救援结束后你可能发现自己莫名处于 Ctrl 按住的状态，屏幕一直缩放或一片文字被拖蓝。

## 11. GUI 的克制原则

四条原则：**设备感知、继承透明、渐进复杂度、一致性**。

- **渐进复杂度**：只用一台设备的用户从头到尾看不到"多设备"概念，界面和他单机时代完全一样；真插了第二台键盘，相关设置才出现。
- **继承透明**：哪个设置是继承默认值、哪个是本设备覆盖，用视觉徽章一眼分清，不用点进去猜。
- **不打断式反馈**：识别设备时不弹模态框让人干等——按键的那一刻，对应设备那一行就地亮起来。
- **一行的取舍**：原生标题栏没法塞自定义按钮，纵向空间又珍贵（键盘可视化本身已经很大块），于是操作按钮、标签页、启动控件合并进同一行。
- **编辑目标常显**：顶栏之外还有一条状态条，随时显示当前正在编辑的「设备 × 应用」范围（全局 / 某设备 / 某应用 / 设备+应用）；加上把「正在给谁配置」提到所有页签之上的应用设置栏，改的是哪套规则永远不用猜。

---

**一致性回顾**：回看所有系统，套路是统一的——遇到**不确定**（tap 还是 hold？组合还是连按？），就去构造明确的判定时机（时间窗、阈值、提前判定相位），而不是到处打补丁；遇到**依赖外部世界**（设备、应用、前台窗口变化），就在入口边界上一次性识别清楚、必要时带快照进场；遇到**故障风险**，就把兜底下沉到离硬件最近的层面。
